## 2. 문제 지점 다섯 개

### ★ P1 — `sk_rcvbuf` 는 정적이고, 정할 자격이 있는 주체가 없다

**어디**: `udp.c:1713` `rcvbuf = READ_ONCE(sk->sk_rcvbuf)` — 읽기만 한다.
갱신하는 코드는 수신 경로 어디에도 없다. TCP 의 `tcp_rcv_space_adjust()`
(DRS) 에 해당하는 것이 **UDP 에는 없다.** 7.2.7 까지 없다 (grep 0 건).

**그래서 값이 어디서 오나** — 셋 중 하나고 셋 다 틀린다:

| 경로 | 코드 | 결과 |
|---|---|---|
| 앱이 아무것도 안 함 | `sock.c:3644` `sk_rcvbuf = sysctl_rmem_default` | **208 KB** |
| 앱이 `SO_RCVBUF` 호출 | `sock.c:1358` `min_t(u32, val, sysctl_rmem_max)` | **조용히 잘림** |
| 관리자가 `rmem_max` 를 올림 | 전 소켓에 일괄 | 어떤 값? 근거 없음 |

가운데 줄이 핵심이다. `sock.c:1358` 은 요청을 `rmem_max` 로 자르고 **에러를 안
돌려준다.** `sock.c:983` 이 그 값을 2 배 해서 넣는다. 그래서:

```
setsockopt(SO_RCVBUF, 64 MB)  →  실제 425,984 B (416 KB) = 요청의 0.6%
반환값은 0 (성공).  getsockopt 로 확인해야만 알 수 있다.
```
(a) 측정으로 직접 확인. 우리 벤치의 `udp_sockopt` 기준선이 정확히 이것이다.

**왜 앱이 못 정하나**: 앱이 알아야 하는 것은 "GRO 가 합친 버스트 하나가 몇
바이트인가" 인데, 그건 ②의 `rx-frames`(DIM 이 런타임에 결정) × ③의 병합 깊이
(펌웨어·MTU·흐름 수에 좌우) 로 정해진다. **앱에게 보이는 인터페이스가 없다.**

**증상** (a): MTU 9000 · 1 flow · 88G 제공에서
```
udp_plain    12.99 Gb/s   busy 66%
udp_sockopt  23.18 Gb/s   busy 73%
우리          52.29 Gb/s   busy 100%
```
**CPU 가 놀면서 버린다.** 일이 모자란 게 아니라 담을 데가 없어서 버린 것이다.
이게 P1 의 가장 깨끗한 증거다.

그리고 소켓 수를 늘리면 기존 UDP 가 저절로 회복한다 (12.99 → 37.57 @16flow).
총 버퍼가 소켓 수에 비례해 늘기 때문. → **208 KB 라는 기본값은 소켓이 많을 때만
우연히 맞는 값**이다.

### ★ P2 — 총량을 보는 주체가 없다

**어디**: 없다는 것이 문제다. `sk_rcvbuf` 는 소켓별이고, 전역 제한인
`sysctl_udp_mem` 은 `udp.c:4039` 에서 **RAM** 으로 정해진다:

```c
limit = nr_free_buffer_pages() / 8;     // udp.c:4039
```

캐시 크기는 한 번도 안 본다. `cache_size|llc_size|l3_size` grep **0 건**
(6.18.53, 7.2.7 둘 다).

**왜 캐시여야 하나** (a, Intel CAT 로 인과 입증):
실제 워킹셋 = **ring descriptor pages + Σ sk_rcvbuf** 이고, 이게 L3 를 넘으면
절벽이 생긴다. CAT 로 L3 를 18/9/4.5 MiB 로 잘라주면 무릎이 10/6/4 MiB 로
따라 움직인다 — 소켓 수와는 무관.

**증상**: 8 MB × 8 소켓 = 64 MB ≫ L3 18 MB → **22.9 Gb/s** (1 MB × 8 은 55.7).
같은 커널, 같은 부하, 버퍼 총량만 다르다.

---

### ★ P3 — 큰 버퍼의 비용은 메모리가 아니라 **producer→consumer 캐시 핸드오프**다

이게 가장 반직관적인 지점이라 따로 잰다. 생산자(NAPI)와 소비자(recvmsg)를
**공유 캐시 레벨만 다르게** 배치하고 버퍼를 512 KB → 18 MB 로 키웠을 때:

| 생산자·소비자가 공유하는 것 | 512K 대비 18M 처리량 비 |
|---|---|
| L2 + L3 (같은 코어) | **0.40** |
| L3 만 (같은 소켓) | **0.61** |
| 없음 (다른 소켓) | **0.94** ← 사실상 무효 |

**잃을 공유 캐시가 없으면 버퍼 크기는 무의미하다.** 즉 큰 버퍼가 나쁜 이유는
"메모리를 많이 써서" 가 아니라, skb 가 큐에 오래 앉아 있는 동안 캐시에서
축출되고 ⑧의 `skb_copy_datagram_msg()` 가 **DRAM 을 때리기 때문**이다.

이 하나로 여러 관측이 동시에 설명된다: MTU 1500 의 평탄한 곡선, 2 코어로
분리했을 때 붕괴가 완화되는 것, 나쁜 상태의 cache-miss 44% / IPC 0.64.

---

### ★ P4 — 버릴 패킷에 일을 다 쓰고 나서 버린다

**어디**: 폐기 판정이 `udp.c:1723` 이다. 그림에서 ⑥ — **①②③④⑤ 를 전부 지난
뒤**다. 버려질 패킷 하나가 이미 소비한 것:

- DMA 와 descriptor 회수
- skb 할당 + 헤더 파싱
- GRO 해시 조회·병합 시도
- IP 경로 조회, UDP 체크섬, 소켓 조회
- (앱이 GRO 를 안 켰으면) `udp_rcv_segment()` 재분할까지

**그리고 이게 자기 강화 루프다**: 과부하에서 폐기가 늘면 → 폐기 작업이 CPU 를
먹고 → 소비자가 더 못 돌고 → 큐가 더 차고 → 폐기가 더 는다. 천장을 넘는 순간
**처리량이 평탄해지는 게 아니라 내려간다** (60G 제공 시 41.8 Gb/s).

측정 (a): 배달된 바이트당 명령어 수 **0.88 → 0.53 (−40%)**.

---

### ★ P5 — 버퍼는 소켓별인데 병목은 큐별

`sk_rcvbuf` 는 소켓마다 있다. 그런데 ①의 ring 도, ②의 NAPI 예산도, 그것들이
먹는 캐시도 전부 **큐** 단위다. 소켓 여덟 개가 큐 하나를 공유하면 각자 자기
버퍼만 보고 자란다. 아무도 합을 모른다.

**증상**: 세 양을 세 주체가 서로 모른 채 정하는데 제약이 셋이나 엮여 있다.

| 양 | 정하는 주체 | 언제 |
|---|---|---|
| ring 크기 | 관리자 (`ethtool -G`) | 부팅 시 |
| `rx-frames` | **DIM 이 런타임에 자동** | 매 순간 |
| `sk_rcvbuf` | 앱 (`setsockopt`) | 소켓 생성 시 |

```
제약 1:  rx-frames ≤ ring                       어기면 rx_out_of_buffer
제약 2:  rx-frames × pktsize ≤ sk_rcvbuf        어기면 소켓 버퍼 넘침
제약 3:  ring_bytes + Σ sk_rcvbuf ≤ LLC         어기면 캐시 절벽
```

**어느 주체도 혼자서는 이 셋을 못 맞춘다.** 실측 (rx-usecs 8 고정, 48G):

| rx-frames | rmem 1M | rmem 8M |
|---|---|---|
| 16 / 32 / 64 | 47.98 | 47.97 |
| 96 | **38.04** | 47.98 |
| **128** ← DIM 이 앉는 곳 | **28.93** | **47.86** |
| 192 | 20.0 | 39.6 |

절벽 위치가 `sk_rcvbuf` 에 따라 96 → 128 로 움직인다 (제약 2). 그리고 ring 을
1024 로 키우면 제약 1 은 사라지지만 16 MB 를 캐시에서 먹어 제약 3 을 위반한다
(8M/frames128: ring 128 **47.86** vs ring 1024 **36.86**, −11 Gb/s).

→ **"rmem 을 N MB 로 맞춰라" 가 원리적으로 불가능하다는 직접 증거.**
   N 은 DIM 이 방금 무엇을 골랐는지에 달려 있고, 앱은 그걸 볼 수 없다.

## 3. 문제 ↔ 설계 대응

| 문제 | 우리 기전 | 어디에 |
|---|---|---|
| P1 정적 버퍼, 정할 주체 없음 | **소비된 양으로 유도** (`target = 2 × 비움주기 최대점유`) | `udp.c` `udp_rcvbuf_autotune()` |
| P2 총량을 보는 주체 없음 | **L3 에서 유도한 전역 예산** (부팅 시 캐시 토폴로지) | `udp_cache_budget()` |
| P3 큰 버퍼의 캐시 비용 | 같은 예산 (상한이 캐시에서 나오므로 자동) | 〃 |
| P4 버릴 패킷에 일을 다 씀 | **드라이버에서 조기 폐기** | `mlx5/en_rx.c` shed 훅 |
| P5 소켓별 버퍼 vs 큐별 병목 | 예산이 **전역**, ring 바이트를 드라이버가 보고 | `net_rx_ring_bytes()` |

**P3 와 P4 는 다른 문제다.** 폐기(일을 줄이는 것)로는 큰 버퍼를 구제하지 못한다:
8 MB × 8 소켓은 shed 를 켜도 22.9 → 29.5 에서 멈춘다 (1 MB + shed 는 55.8).
**캐시를 밀어내는 것은 일이 아니라 용량이고, 용량은 cap 으로만 줄어든다.**

## 4. 이 스택에서 우리가 **안 건드린** 것 (그리고 왜)

- **⑦의 락**: `__skb_recv_udp()` 는 `reader_queue` 를 먼저 보고 비었을 때만
  `sk_receive_queue` 락을 잡아 통째로 splice 한다 (`udp.c:1953`). 경쟁 락은
  배치당 1 회다. upstream(Abeni 의 reader_queue)이 이미 해결했다.
  → 우리 패치 0001~0004 를 폐기한 이유.
- **⑥의 enqueue 배치화**: 6.18 upstream 이 per-NUMA `udp_prod_queue` llist 로
  `busylock` 을 대체했다 (`udp.c:1718`). 우리 0003 보다 낫다.
- **⑤의 재분할**: 앱이 `UDP_GRO` 를 켜면 안 일어난다. 앱 측 한 줄로 고쳐지는
  것을 커널에서 우회하는 것은 범위 밖. (단, 못 켜는 앱을 위한 엣지케이스로 후순위)
- **②의 DIM 자체**: 40G 이하에서 CPU 를 15~17%p **절약한다.** 없애면 손해다.
  우리 코드에 DIM 을 인지하는 부분은 한 줄도 없고, 그래도 커버되는 이유는
  점유율이 버스트의 *원인*을 묻지 않고 *결과*에만 반응하기 때문이다.
