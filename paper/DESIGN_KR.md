# UDP 수신 경로 재설계 — 무엇이 문제였고 어떻게 고쳤는가

랩미팅 발표용. 측정은 전부 sslab3 → sslab4, 100GbE ConnectX-5, 단일 수신 코어,
DIM on, 커널 GRO on, 앱이 `setsockopt(UDP_GRO)` 설정.

---

## 0. 출발점

전송 프로토콜은 사실상 둘뿐이다. TCP 는 확인응답·재전송·혼잡제어를 하고,
UDP 는 포트와 체크섬만 붙인다. **UDP 가 덜 하므로, 손실을 감당할 수 있는
상황이면 더 빨라야 한다.**

100GbE 한 코어에서 재면 반대다. 그리고 **"UDP 가 느리다" 로 뭉뚱그리면 안 된다** -
기준선이 셋이고, 셋 다 의미가 다르다 (MTU 9000, 단일 흐름, 56G 제공):

| 기준선 | 실제 버퍼 | 처리량 |
|---|---|---|
| 앱이 `setsockopt` 를 안 부름 | 208 KB | **8.96** |
| **앱이 `SO_RCVBUF` 64MB 를 요청** | **416 KB** | **15.4** |
| 관리자가 손으로 최적값을 찾아 넣음 | 2 MB | 55.45 |
| TCP (아무 설정 없이) | 자동 | 55.7 |

**두 번째 줄이 핵심이다.** 앱이 정석대로 64MB 를 요청해도 416KB 를 받는다 -
`rmem_max` 의 기본값도 208KB 이고 커널이 2 배를 주기 때문이다. 요청의 **0.6%**
이고, `setsockopt` 는 **성공을 반환한다.** 앱은 자기가 못 받았다는 것을 모른다.

즉 문제는 "기본값이 낮다" 가 아니다. 그건 올리면 된다. 실제 문제는:

1. 앱이 정석대로 요청해도 조용히 잘린다
2. 관리자가 `rmem_max` 를 올려도 **얼마를 넣을지는 아무도 모른다**
3. **조건마다 정답이 10 배 다르다** (208KB ~ 2MB, 4 장 참조)

이유는 데이터그램 경로의 명령어 수가 아니다 — 그건 여전히 UDP 가 짧다.
TCP 주위에 쌓인 것이 UDP 주위엔 없다는 것이다. TCP 는 2004 년부터 수신 버퍼를
스스로 맞춘다(`tcp_rcv_space_adjust`). **UDP 에는 그 기능이 어느 커널 버전에도
없다.** `rmem_default` 를 받고 끝이다.

## 1. 문제: 아무도 버퍼 크기를 정할 위치에 없다

### P1. 담아야 할 버스트 크기를 앱이 볼 수 없다

NIC 은 패킷마다 인터럽트를 걸지 않고 `rx-frames` 개를 모아서 건다. 우리 하드웨어
에서 DIM 이 128 을 고르고, MTU 9000 이면 **인터럽트 한 번에 약 1.15MB** 가
도착한다. 그동안 소비자는 직전 것을 처리 중이므로 버퍼가 그걸 담아야 한다.

그런데 **그 128 을 앱은 볼 수 없고, 드라이버가 런타임에 바꾼다.**
`lib/dim/net_dim.c` 의 hill climbing 이 bytes/ms 가 나아지는 쪽으로 인덱스를
옮기다 봉우리에서 멈추는데, 봉우리 위치는 링크 속도·코어 성능·트래픽 패턴에
따라 달라진다. 모드가 CQE 냐 EQE 냐에 따라 테이블도 다르다(128 vs 256).

측정 — `rx-frames` 를 고정하고 스윕 (48G, sd≈0.00):

| rx-frames | 버퍼 1MB | 버퍼 8MB |
|---|---|---|
| 16 / 32 / 64 | 47.98 | 47.97 |
| 96 | **38.04** | 47.98 |
| **128** ← DIM 이 앉는 곳 | **28.93** | 47.86 |

**무릎이 버퍼 크기에 따라 움직인다.**

### P2. 써도 되는 총량이 전역이고, 어느 소켓도 못 본다

처리량은 **수신 경로가 만지는 총량** — NIC descriptor 페이지 + 모든 소켓의
큐잉된 데이터 — 이 LLC 를 넘으면 절벽처럼 떨어진다.

절벽이 캐시라는 것은 **인과적으로** 보였다. Intel CAT 로 L3 를 18 → 9 → 4.5 MiB
로 자르면 무릎이 **10 → 6 → 4 MiB 워킹셋**으로 따라 움직인다. 다른 것은
아무것도 바꾸지 않았다.

그리고 임계는 **합**의 성질이다. 소켓 8 개 × 2MB 와 소켓 1 개 × 16MB 가 같은
지점에서 무너진다. **소켓별 한도로는 표현할 수 없다** — 8MB 는 한 소켓에
안전하고 여덟 번째로는 파괴적이다.

### P3. 소비 능력을 넘으면 큰 버퍼가 오히려 해롭다

큰 버퍼의 비용은 메모리가 아니라 **핸드오프**다. producer(NAPI)와
consumer(recvmsg)를 분리해 **공유 캐시 레벨만** 바꾸고 버퍼를 512KB→18MB 로
스윕하면:

| 공유 캐시 | 처리량 비 |
|---|---|
| L2 + L3 (같은 코어) | **0.40** |
| L3 만 | 0.61 |
| 없음 (다른 소켓) | **0.94** |

공유할 캐시가 없으면 버퍼 크기가 거의 무의미하다. 즉 작은 버퍼의 데이터는
소비자가 도착할 때 아직 캐시에 있고, 큰 버퍼의 것은 축출됐다.

따라서 **"넘치면 키워라"는 천장 너머에서 방향이 반대다.**

### P4. 버릴 패킷에 일을 다 쓴다

소켓에서 drop 되는 패킷은 이미 descriptor 처리, `skb` 할당, GRO, route lookup
을 다 썼다. 과부하에서 수신 코어는 **버릴 패킷을 처리하느라** 대부분을 쓴다 —
그래서 **CPU 가 남는데 처리량이 무너진다** (56G 제공에 busy 63%, 배달 33G).

### P5. 버퍼는 소켓별인데 병목은 큐별

TCP 와 UDP 가 한 수신 큐를 공유하면, UDP 버퍼를 어떻게 조절해도 TCP 몫이
생기지 않는다. TCP 가 부족한 것은 공간이 아니라 **서비스**다. 배분으로는
프로토콜 간 조정이 불가능하다.

## 2. 설계

세 메커니즘. 각각 위 문제에 대응한다.

### M1 — 소비된 양으로 버퍼 크기를 유도 (P1, P3)

TCP 의 규칙은 `rcvbuf = 2 × (1 RTT 동안 앱에 전달된 바이트)` 다. RTT 의 역할은
**소비자가 한 바퀴 도는 시간**을 구분하는 것이고, UDP 에도 그런 주기가 있다:
**큐가 찼다가 비기까지**.

```
target = 2 × (한 주기 동안 소비자가 가져간 바이트)
```

`net/ipv4/udp.c` 의 `udp_rcvbuf_autotune()`.

- **주기는 양끝으로 정의한다** — 절반 넘게 찼다가 1/8 아래로 내려와야 한 주기.
  드레인만 보면 빈 큐에 패킷 하나 올 때마다 "주기 완료"가 되어 목표가 0 으로
  덮어써진다 (실제로 그렇게 실패했다).
- **큐 깊이가 아니라 소비량을 센다** — 깊이는 `sk_rcvbuf` 에 상한이 걸려서,
  버퍼를 키우면 관측되는 수요도 커지는 되먹임이 생긴다 (9.4MB 까지 폭주했다).
  TCP 가 "앱에 전달된 바이트"를 세는 것과 같은 이유다.
- 소비자가 못 따라가는 소켓은 큐가 안 비므로 주기가 완성되지 않고, **목표가
  안 생겨 자라지 않는다.** P3 의 경우가 스스로 제외된다.

### M2 — 캐시에서 유도한 전역 상한 (P2)

```
허용량 = (LLC − 활성 수신링이 쓰는 바이트) × pct        기본 pct = 50
```

- LLC 는 부팅 시 커널 캐시 토폴로지에서 읽는다 → 기계를 따라간다
- **활성 수신링**: 드라이버가 자기 링의 바이트를 등록하고, 패킷을 받을 때마다
  타임스탬프를 갱신한다. 합산할 때 최근 1 초 내 활동한 링만 센다.
  - 변환이 드라이버에 있는 이유: `ethtool` 은 **엔트리 수**를 주는데 mlx5 의
    multi-packet WQE 는 엔트리마다 페이지 여러 개를 달아 1024 엔트리가 4MB 가
    아니라 **16MB** 다. 포맷을 아는 쪽만 바이트로 낼 수 있다.
  - 활성만 세는 이유: 기본 설정은 코어 수만큼(여기선 **24개**) 링이 있지만
    트래픽은 그중 일부에만 온다. 전부 세면 허용량이 0 이 되어 버퍼가 붕괴한다
    (실제로 그렇게 실패했다 — 4.35 Gbps).
  - 감소를 **읽는 쪽**에서 하는 이유: 조용해진 링은 폴링되지 않으므로 스스로
    조용함을 알릴 수 없다.
- 소켓이 처음 패킷을 받을 때 **버퍼 전체**를 합계에 더한다. 증분만 세면
  기본 크기가 안 보이는데, 소켓이 많으면 그게 대부분이다 (8 × 1MB = 8MB).
- 넘으면 sweep 이 각 소켓을 **공평 몫(허용량÷소켓수)** 으로 끌어내린다.
  생성 시 거절하면 먼저 온 소켓이 다 먹는다.
- **상한이지 목표가 아니다.** 그 안에서 크기는 M1 이 정한다.

### M3 — 드라이버에서 조기 폐기 (P4, P5)

소켓 drop 이 난 큐를 표시하고, 짧은 창(50µs) 동안 드라이버가 **`skb` 를 만들기
전에** UDP 완료를 버린다. `mlx5e_handle_rx_cqe()`.

- 큐는 **소켓이 아니라 패킷**에서 읽는다. `sk_rx_queue_get()` 은 connected
  소켓에만 유지되어, unconnected(다수 sender) 소켓은 −1 을 돌려주고 fallback 이
  큐 0 으로 바꾼다 → 멀티큐에서 전부 큐 0 만 조인다.
- CQE 에 L4 타입이 있어 **UDP 만** 골라 버릴 수 있다 → P5.

## 3. 왜 이 조합인가

**두 실패는 성질이 다르다.**

| | 고칠 수 있나 |
|---|---|
| 버스트에 비해 **작은** 버퍼 | **사후에 싸게** — 일을 안 하면 됨 (M3) |
| 캐시에 비해 **큰** 버퍼 | **불가** — 버퍼가 생기기 전에 막아야 함 (M2) |

측정 (8 소켓, `rmem_default` = 8MB, 합 64MB):

| | 처리량 | 손실 |
|---|---|---|
| cap 없음 | 22.5 | 59.9% |
| cap 없음 + 폐기 | 30.3 | 45.9% |
| **cap** | **55.0** | 1.8% |
| 처음부터 1MB 였다면 | 55.8 | 0.3% |

**폐기로는 30.3 까지밖에 못 간다.** 일을 줄이는 것과 용량을 줄이는 것은 다르고,
캐시를 밀어내는 것은 용량이다.

## 4. 이식성

기계마다 손봐야 하는 상수를 없애는 것이 목표였다.

| | 어떻게 얻나 |
|---|---|
| L3 크기 | 부팅 시 커널 캐시 토폴로지 |
| 수신링이 쓰는 캐시 | 드라이버가 바이트로 보고 |
| 활성 링 수 | 트래픽으로 판단 |
| 버스트 크기 | 관측된 소비량 |
| 버퍼 크기 | 위에서 유도 |
| `pct` | **유일한 설정값** (기본 50). 뜻이 "NIC 이 쓰고 남은 것의 절반" 으로 고정 |

검증 — `pct=50` 을 **한 번도 안 건드리고** ring 만 바꿨을 때:

| ring | 활성 링 | cap 이 준 허용량 | 처리량 |
|---|---|---|---|
| 1024 (드라이버 기본) | 16 MB | **1.0 MB** | **51.8** |
| 128 | 2 MB | **8.0 MB** | **52.7** |

허용량이 자동으로 8 배 달라진다.

그리고 최적 버퍼 크기가 조건에 따라 실제로 움직인다는 것도 확인했다:

| 조건 | 조건별 최적 static |
|---|---|
| MTU9000 · 1소켓 | 2 MB |
| MTU9000 · 8소켓 | 1 MB |
| MTU1500 · 1소켓 | 1 MB |
| MTU1500 · 8소켓 | 208 KB |

조건별 최적 대비 최악 거리: static 208K **−73%**, static 1M **−7.7%**,
**유도 −5.5%**. 어떤 단일 static 값도 어딘가에서 크게 벗어나고, 유도만 전 조건
6% 이내다.

읽어야 할 것 네 가지:

1. **기존 UDP 의 붕괴는 "소켓 하나 · 큰 MTU" 에서 가장 크다.** MTU 9000·1flow 에서
   plain 12.99 / sockopt 23.18 인데 **CPU 는 66% / 73% 로 놀고 있다.** 일이 모자란
   게 아니라 담을 데가 없어서 버린 것이다. 같은 칸에서 우리는 52.29 (busy 100%).
2. **소켓 수가 늘면 기존 UDP 가 저절로 회복한다** (9000: 12.99→37.57). 총 버퍼가
   소켓 수에 비례해 늘기 때문이다. 즉 리눅스 기본값 208KB 는 **소켓이 많을 때만
   우연히 맞는 값**이다. 하나짜리 흐름에는 8 배 모자라고, 16 개짜리에는 대략 맞다.
   우리 쪽은 반대로 소켓 수에 거의 평탄하다 — 전역 상한이 있기 때문이다.
3. **MTU 3000 이상에서 TCP 와 대등**(기하평균 0.98)한 반면, 기존 UDP 는 어느
   조합에서도 TCP 근처에 못 간다. UDP 가 TCP 에 뒤지는 이유가 프로토콜이 아니라
   **버퍼를 정할 주체가 없어서**였다는 주장의 가장 직접적인 증거다.
4. **MTU 1500 은 전 flow 에서 TCP 에 진다** (×0.73~0.84). 아래 한계에 적는다.

그래프: `figs/grid_tput_m{1500..9000}.pdf` (x축 flow 수),
`figs/grid_tput_f{1,2,4,8,16}.pdf` (x축 MTU), `figs/grid_tput_summary.pdf`.

## 5. 한계 (정직하게)

- **MTU 1500 에서는 TCP 에 진다** (전 flow 수, ×0.73~0.84). 기존 UDP 대비로는
  여전히 최대 4 배지만 TCP 를 못 따라간다. 1500 은 바이트당 패킷 수가 6 배라
  per-packet 비용이 지배하고, **버퍼 크기는 그 비용에 아무 지렛대가 없다.**
  우리가 고친 것은 "담을 데" 이지 "패킷당 일" 이 아니다. GRO 병합 깊이가
  `MAX_SKB_FRAGS 17` 에 묶여 있는 것(이 NIC 에서는 펌웨어가 상한)이 이 구간의
  진짜 제약으로 보인다 — (c) 검증 필요.
- **큐가 많을 때 미검증.** 모든 측정이 단일코어(큐 1개)다. 기본값은 24개이고,
  거기서 동작은 확인했지만 축 전체는 안 쟀다.
- **폐기가 무차별.** 창 안의 UDP 를 가리지 않고 버려서 지연 민감 흐름도 잃는다
  (프로브 손실 11%, 폐기 없을 때 0.2%). 흐름별 선별은 미구현.
- **드라이버 변경이 필요하다.** 폐기와 링 보고 둘 다 mlx5 패치다. 버퍼 sizing 과
  cap 의 계산 자체는 드라이버 무관이지만, cap 의 입력 하나가 드라이버에서 온다.
- **NIC 하나, 캐시 토폴로지 하나.** 다른 하드웨어는 미검증.
- **DIM off / 앱이 GRO 미설정**은 범위에서 제외 (엣지케이스로 후순위).

## 부록: 코드에서 찾는 법

우리가 추가·수정한 모든 구간에 태그가 있다:

```
grep -rn "UDP-optimize" <kernel-tree>
```

| 파일 | 무엇 |
|---|---|
| `net/ipv4/udp.c` | M1 sizing, M2 cap + sweep |
| `include/linux/udp.h` | 소켓별 상태 (목표값, 주기 감지, 계상) |
| `include/net/netns/ipv4.h`, `net/ipv4/sysctl_net_ipv4.c` | `udp_rmem` 삼중값 등 sysctl |
| `include/linux/netdevice.h`, `net/core/dev.c` | 활성 수신링 캐시 회계 |
| `drivers/.../mlx5/core/en_main.c` | 링 등록/해제, 바이트 계산 |
| `drivers/.../mlx5/core/en_rx.c` | M3 폐기, 링 활성 보고 |
| `drivers/.../mlx5/core/en.h` | `MLX5E_RX_MAX_HEAD`, 슬롯 필드 |

sysctl:

```
net.ipv4.udp_rmem = <min> <default> <max>    # tcp_rmem 과 같은 모양
net.ipv4.udp_rmem_autotune  = 0|1            # M1
net.ipv4.udp_rmem_cache_pct = 0..100         # M2 (0 이면 끔)
net.ipv4.udp_rx_shed        = 0|1            # M3
net.ipv4.udp_rx_shed_us     = 50             # M3 창
```

전부 default off 이므로 knob 을 안 건드리면 upstream 과 동작이 같다.
