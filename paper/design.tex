\section{Design}
\label{sec:design}

\sys is two mechanisms and no controller: a global allowance that caps what
receive buffers may sum to, derived from the cache the kernel reads at boot, and
a driver-side discard that stops building socket buffers the consumer will not
reach. \S\ref{sec:sizing} reports the adaptive sizer we built first, and why it
is not part of the system.

\subsection{A cap derived from the cache}
\label{sec:allowance}

\sys reads the last-level cache size from the kernel's cache topology at boot
and takes a configurable fraction of it, one half by default, as the allowance.
A socket's whole buffer is charged against the total once, on the first packet
it receives, and returned when it is destroyed.

\paragraph{What the implemented cap does, and does not.} It refuses any
\emph{increase} that would take the total past the allowance. It does not
currently refuse the buffer a socket starts with: a machine configured with an
8\,MB \texttt{rmem\_default} and eight sockets is charged 64\,MB and permitted
it. The measurement in Table~\ref{tab:nostatic} that shows discarding failing to
rescue eight 8\,MB buffers is therefore evidence that such a cap is \emph{needed},
not that ours enforces it, and we are explicit about the distinction. Clamping
the default---as opposed to an explicit \texttt{SO\_RCVBUF}, which we argue
below should be honoured---is the obvious extension and the one we would make
next; it requires deciding what a socket gets when the allowance is already
spent, which is a policy question we have not measured our way to an answer on.

\paragraph{A cap, not a target.} The allowance does not look for a good size. It
prevents a set of individually reasonable sizes from summing to a bad one, which
is the failure a per-socket limit cannot express: 8\,MB is entirely safe for one
socket and ruinous as the eighth. Within the allowance, what the application or
operator asked for stands.

This is a weaker mechanism than the sizer we replaced it with, and that is the
point. \S\ref{sec:workingset} says the threshold is a property of the sum, not
of any socket, and says nothing about where within the bound a given socket
should sit. A cap is the mechanism that claim licenses.

\paragraph{What is charged.} The whole buffer, not the part above some default.
Counting only what exceeds a baseline leaves the baseline invisible, and the
baseline is not small when there are many sockets: eight at a 1\,MB default are
8\,MB of a 9\,MB allowance before anything else happens. We learned this the
expensive way---an earlier version charged only what it had itself handed out,
and eight sockets reached 17.8\,MB against a 9\,MB allowance.

\paragraph{Capacity, not occupancy.} The allowance bounds granted capacity
rather than queued bytes. Bounding queued bytes is the natural first attempt and
does not work: while the consumer keeps up the queues sit nearly empty---0.36\,MB
held against 8\,MB of capacity in one measurement---so the bound does not bite
until the queues have already grown deep, by which point the buffers behind them
are far too large. Occupancy follows capacity, not the reverse.

\paragraph{Sockets that set \texttt{SO\_RCVBUF}.} An application that names a
size still receives it. Overriding an explicit request would break a long
standing expectation, and in isolation the request is rarely the problem. \sys
charges such a socket for what it holds so that everyone else stops compounding
it: 64\,MB is entirely safe until it is the eighth one.

\paragraph{Why the fraction is an operator setting.} We would prefer the
allowance to be fully derived, and it nearly is---the cache size comes from the
kernel's own topology, so it follows the hardware. What the kernel cannot see
from the socket layer is how much of that cache is already committed. The
dominant unseen term is the NIC's descriptor pages, 16\,MB for a 1024-entry ring
on our hardware, which the driver allocates and never surfaces in a form the
socket layer can query; a second is other tenants on the same ways. A fully
automatic version is possible---the driver knows both the ring size and the
descriptor format---but it would put the mechanism behind a per-driver change,
and one number per machine is a considerably better interface than one number
per socket.

\subsection{Discarding at the driver}
\label{sec:shed}

A cap keeps buffers from summing past the cache. It does nothing about a burst
larger than one socket's buffer, which is the other half of the problem, and
neither does any buffer once the receiving core is saturated: past that point
the queue is full at every size.

What is available there is not to do the work. A packet that will be dropped at
the socket has by then cost descriptor processing, an \texttt{skb} allocation,
GRO, and a route lookup. \sys marks the receive queue on which a socket drop
occurred, and for a short window---50\,\textmu s by default---the driver
discards UDP completions before building an \texttt{skb}, identifying them from
the completion descriptor's L4 type.

\paragraph{The window is fixed.} We swept it from 25\,\textmu s to 1600 and
found the response markedly asymmetric: too short costs 7\%, too long costs
67\%, and a window of 1600\,\textmu s is worse under a load transition than no
window at all. An adaptive controller is available but unnecessary---the
oracle's advantage over a fixed 50\,\textmu s is 1.6\%, less than the cost of
searching for it.

\paragraph{Take the queue from the packet.} The queue to hold back is the one
that delivered the packet that could not be queued. Reading it from the socket
instead, via \texttt{sk\_rx\_queue\_get()}, is wrong in a way that only appears
with more than one queue: that field is maintained for connected sockets, and an
unconnected socket---the many-senders case UDP exists for---reads back $-1$,
which a fallback turns into queue zero. Every such socket then throttles queue
zero no matter which queue was drowning.

\paragraph{Selectivity is the point.} Buffers are per socket; the resource under
contention here is a queue. When TCP and UDP share one, no amount of UDP buffer
tuning gives TCP its share, because what TCP is short of is not buffer. A
discard keyed on the L4 type can make room for one protocol by not doing work
for another, which allocation structurally cannot.
